# cover-skill-plan 设计诊断：一次真实运行的教训

日期：2026-11-11。对象：`mine/cover-skill-plan`（与正本 `/Users/shay/.agents/skills/cover-skill-plan` 同版）。
证据：本次真实任务「咖啡冲煮方案 · 豆仓管理」7 页卡片的完整运行记录（`.runs/coffee-20261111/work/`：源片段、池、计划、qa-report）。
本文只诊断 skill 本身的设计问题，不评价交付物——交付物只是机制的结果。

---

## 0. 一句话结论

**skill 的架构承诺是"LLM 负责排版，工具负责验证"，但它把排版所需的几何信息、搭配先验、锚点约定全部留在了种子 CSS 和运行时渲染里，LLM 看不见也拿不到；于是每一次排版决策都是盲决策，只能用"渲染→报错→改→全量重跑"的高成本反馈回路兜底。**

这次运行 30 分钟、38 积分、gate 跑了 7 轮（前 5 轮几何失败），7 点目检质量问题——全部不是偶然失误，而是这一结构性缺口的必然产物。

---

## 1. 现象层：七点目检 → 机制映射

用户目检发现的每个"不对劲"，都能定位到 skill 的具体设计位置。没有一个属于"LLM 手滑"，全部属于"skill 没给约束或没给信息"。

| 目检现象 | 表面原因 | 机制真相（代码位置） |
|---|---|---|
| 01 封面手机模型变小 | 出血位置飘了？ | 出血位置是种子**写死**的（`.cover-bleed`：宽 54cqw、出画 22cqw，seed L67）；变小的是手机本身——54cqw 宽 × 壳比例 910/1806 ≈ 1157px 高，与两行大标题在垂直预算里冲突，gate 报 R1 越界，LLM 只能内联 `width:46cqw` 收窄（p01.part.html 可见）。种子锁了宽，没锁"宽 × 标题行数"的联动预算 |
| 01/02/03 text-block 抢主体 | 字色字号不一致 | `.text-block` = 全墨色 `--ink` + 2.6cqw（seed L112），比 fcard 说明字（muted 1.6cqw）重两级。⚠️ 更要命的是 L17 **禁止内联改 `font*`/`color`**——LLM 即便意识到抢主体，也没有任何手段弱化它，只能不用或挪走。组件只有一个视觉档，调整通道又被封死 |
| 02 复选框没勾上 | 忘了勾？ | 组件目录明确写着变体："done 表示勾选；不加 done 就是空框，两者都可用"。LLM 选空框是刻意的（痛点清单配"你中了几条"的读法）。真正的缺口是：**这个变体决策不写进 plan**，目检者无从分辨"刻意"还是"遗漏" |
| 02 悬浮字位置漂移 | 组件坏了？ | `.ghost{position:absolute;right:0;bottom:8cqw}` 锚定的是**最近的定位祖先**。overlay 放在 `main.body` 里就锚 body，直接放 `.p-page` 下就锚整幅画布——同一个组件，DOM 落点不同，视觉位置就不同。种子和文档都没规定 overlay 必须放哪 |
| 03 手机被 1:1 分栏压小 | 布局失误？ | 你的判断完全正确，这是最典型的一例：`.flow-row>.region{flex:1 1 0}` 左右强制均分，`phone` 宽度受列宽 `max-width:100%` 钳制、比例又是写死的 910/1806，**列一窄壳必缩**。种子里唯一的"主体优先"特例是封面 `.cover-bleed`——作者意识到过这个问题，但只给封面做了，内页没有 |
| 03 多了一条横线 | 哪来的组件？ | 不是独立组件，是 serif（quote 组）自带的分隔线 `.rule`。目录说"缺哪项就省哪个节点"，LLM 保了 rule、省了 source——规则上合法，视觉上无意义。**rule 的存在感依赖出处节点成立，这条依赖关系没写进目录** |
| 04 手机下注解太长 | 文案问题 | 单机注解无任何约束：`.phone-cell` 小字档（2.1cqw 居中加粗）只在多机并排时由 L19 强制；单机场景 LLM 用了普通 text-block（全强度正文档），目录也没写"单机注解可省" |
| 05 区域内动态组件搭配差 | 选得不好？ | 配方 `allow` 只回答"准不准"（白名单），不回答"搭不搭"（先验）。P05/P06 的 allow 列表给了 4–5 种组件任意混搭，没有任何组合约束 |
| 06 金句页用了黑 | 默认黑？ | 其实是文档引导的结果：paper-journal.md 写"dark 通常留给需要沉下来的收束页或证据页"，金句收束页正好命中。机制缺口：dark 是 LLM 的自由开关，只有一句软话，**没有"用户未要求时默认不用"的硬约束，也没有用户偏好通道** |
| 07 结尾页太空 | 内容少了？ | P12 的 allow 给了 8 种组件随意选、不设密度下限；密度检查 R7 只是 WARN。最简组合一路绿灯，目检才暴露 |

## 2. 机制层：四个根因

### 根因 1：错误后置暴露 + 按页早停 = 错误挤牙膏式出现

检查链的顺序是：静态来源校验（L8/L14/L15）先跑 → 浏览器渲染 → 几何检查（R1 越界/R2 遮挡）。而**真正致命的布局错误全部在后半段**。LLM 写页面时，对"这段文字和这只手机会不会互相挤压"零信息。

更糟的是 [02-constraints.md](../references/02-constraints.md) 明文规定：lint 与几何**按页早停**——"遇到第一个含 ERROR 的页就停止枚举后续页"。这个设计的本意是省时，但在返修循环里它产生了反效果：

```
轮1: P01 报错 → 修 P01
轮2: P01 过了 → P03 报错 → 修 P03
轮3: P03 过了 → P04 报错 → 修 P04
……
```

每轮只揭一批错，修完重跑又揭下一页的。本次 P01 修 3 轮、P04 修 3 轮，就是这个机制一格一格挤出来的。**早停省下的是单轮检查时间，付出的是成倍的总轮数。**

### 根因 2：组件内在几何对 LLM 不可见（盲写困境）

组件目录（components.json）给 LLM 的是语义描述——"手机模型""账行""浮动卡片"——**不含任何几何参数**。而真正的尺寸约束全部埋在种子 CSS 里：

| 隐藏尺寸 | 值 | 后果 |
|---|---|---|
| `phone` min-height | 48cqw ≈ 518px | 区域高度给不出就是 R1 越界，LLM 写前无法预判 |
| `phone` 比例 + max-width | 910/1806 + 列宽钳制 | 分栏变窄壳必缩（03 页实例） |
| `ledger .n` | 7cqw 衬线大字 | 长数字 + 单位 × 列宽冲突，渲染后才量出来（04 页实例，修了 3 轮） |
| `fcard` max-width | 42cqw | 多卡并排时空间预算隐性受限 |
| `.cover-bleed` | 54cqw 宽 | 与标题行数的联动预算没人算 |

这是纯浪费。这些数字本可以在写页面前就进入 LLM 的决策输入。**决策的后果发生在渲染层，决策的输入却只给到语义层——这个信息断层是所有返修的总根源。**

### 根因 3：全量重跑的反馈成本

文档规定："纯结构与文案的返修可 `--no-shot` 快查，**涉及构图与尺寸的改动必须全量重查**"。而几何返修**必然**涉及尺寸——于是每一次返修都是：起 Chrome → build 全部 7 页 → 渲染 → 全部截图。机制上没有任何"只重查受影响页"或"轻量预检"的能力。

成本模型：

```
单轮全量 gate ≈ Chrome 启动 + 7 页构建 + 7 页渲染测量 + 7 页截图
返修轮数 × 单轮成本 = 固定开销无法摊薄，且轮数本身被根因 1/2 推高
```

三个机制叠加：根因 2 决定了**必须**靠渲染发现问题（盲写），根因 1 决定了**每轮只能**发现一部分问题（早停），根因 3 决定了**每轮都付全价**（全量重跑）。30 分钟 / 38 积分就是这三条曲线的乘积。

### 根因 4：allow 自由组合，没有搭配先验

配方目录的区域定义（[recipes.json](../config/recipes.json)）只回答两个问题：这区**允许**什么（`allow`）、某组件**最多**几个（`max`）。它不回答"这些组件放在一起**好不好**"。

- P05 left：`mn / text-block / list / fcard / phone` 五选任意混搭；
- P03 right：`mn / phone / shot` 任选，无配对约束；
- P12 full：8 种组件不设密度下限。

自由度本身不是错，错在**自由度与支撑自由度的先验不配套**。每页 LLM 都要在白名单里自行组合、自行承担布局后果，组合失败的概率就变成了 gate 失败的概率。这次运行验证得很干净：**所有 5 轮几何失败都发生在"自由组合"的页面上，所有返修都在为组合后果买单。**

它同时是质量问题和经济问题的共同根源——不是它让 LLM"反复思考浪费时间"，而是它让每页的布局决策没有先验约束，只能靠渲染验证兜底，而兜底是昂贵的（见根因 1–3）。

## 3. 结构层：为什么会设计成这样

回看 skill 的三条核心设计决策，每一条单独看都合理，**叠加在一起**却制造了失衡：

| 设计决策 | 出发点 | 付出的代价 |
|---|---|---|
| **自然流排版**：布局交给 flex/grid 流式原语，不在生成期预计算坐标 | 正确——避开脆弱的坐标排版，组件随内容伸缩 | 流式排版的结果由**浏览器**决定，而决策者是**LLM**——两者之间没有信息通道 |
| **allow 白名单**：区域只管准不准，摆位与条数交给当期内容 | 正确——保留表达自由，避免配方僵化 | 白名单是必要条件不是充分条件，"合法但不搭"的组合全部放行 |
| **渲染后验证**：gate 以真实几何为唯一权威 | 正确——比任何静态估算诚实 | 验证是**事后**的、**全量**的、**逐页揭错**的，反馈回路又贵又长 |

三条决策各自守住了一个正确的原则（不预计算坐标、不锁摆位、不虚报验证），但它们共同违反了另一个更基本的原则：

> 📌 **决策输入完备性：LLM 拥有决策权的事项，其决策所需的信息必须以 LLM 可读的形式前置供给。**

skill 把排版权给了 LLM，却把排版的几何后果锁在 CSS 和浏览器里；把组件选择权给了 LLM，却不给搭配的经验先验；把返修的判断权给了 LLM，却让返修的反馈以"每轮揭一批 + 全价重跑"的形式到达。**权力和信息错位**——这是这次运行全部成本与质量问题的同一个来源。

一个值得记下的推论：`cover-bleed` 是种子里的特例，它证明了作者已经为"主体尺寸必须确定"付过一次学费，但只把它做成了封面专用类。**当一个约束在某个场景被手工解决过，它就应该被抽象成所有同类场景的原语**——这条没有做，于是同样的学费在内页又被收了一次（03 页手机被压小）。

## 4. 改进方向（对准机制，按杠杆大小排序）

### A 级：直接消除盲写困境（降轮数、降积分）

1. **几何前置**——组件目录登记关键内在尺寸：`phone` min-height 48cqw / 比例与 max-width 钳制、`ledger .n` 7cqw、`fcard` max-width 42cqw、`.cover-bleed` 54cqw 与出画量。让 LLM 写页面前就能做预算。更彻底的做法：gate 增加"渲染量几何但不判不截"的预检模式，写完先看数字再定稿。
2. **静态检查收集全页再报**——早停保留在几何阶段可以接受（渲染成本高），静态 lint 一次报全所有页的错误。仅此一条就能把本次 7 轮压到 3–4 轮。
3. **分页增量重查**——几何返修提供"只重查改动页"模式（受影响页 = 改动页 + 与其共享空间预算的骨架区），全量 gate 保留给交付前最后一次。

### B 级：收紧自由度与先验的错位（同时改善质量与成本）

4. **区域搭配升级为命名搭配档**——把高频组合做成"区域类 = 组件搭配 + 布局参数"的打包原语（机制参照 `.cover-bleed` 的成功先例），如"左文右机档"（文字列 flex 收缩 + 手机列按内容定宽，先锁主体再分文字——正是目检 03 提出的原则）。配方的 `allow` 降级为兜底白名单，搭配档是首选路径。**搭配档确定，LLM 不再自由发挥，冲突概率和返修轮次同步下降。**
5. **主体尺寸优先原语**（4 的核心内容，单列强调）：给 `phone` / `shot` 登记显式宽度档位，或提供"主体列固定 / 旁列收缩"的 flow-row 变体。把"先保证主体，再处理文字"从目检经验变成种子原语。

### C 级：组件粒度的修正（质量收尾）

6. **text-block 增加弱档**：登记 muted / 小字变体，或目录明确"次要说明用 .d/.n 字段组件"。否则 L17 封死内联调整后，text-block 只剩"全强度"一个档，永远存在抢主体的风险。
7. **overlay 锚点唯一化**：文档规定 overlay 只能放固定位置（建议 `.p-page` 直接子级），ghost 的 `right:0/bottom:8cqw` 从此语义唯一。
8. **rule 与 source 绑定**：目录补一句"省出处时连 rule 一起省"——装饰节点的存在感依赖内容节点，这条依赖必须写明。
9. **dark 默认关**：风格文档改为"默认不用，用户点名或配方声明才开"；或增加 `config/` 用户偏好字段（现成的 `fonts.user.json` 模式可以复用）。
10. **单机注解约束**：目录补"单机下注解尽量省，需要时必须走 `.phone-cell` 小字档"。
11. **变体决策入 plan**：ck 勾选态这类"同一组件多视觉变体"的选择写进计划 intent，让目检可核对是刻意还是遗漏。

## 5. 补充排查：同类问题的系统性扫描

第一轮诊断是**顺着用户目检回溯**的——七点现象查清了，但不等于全貌。按已确认的六个问题类别对种子 CSS、组件目录、配方目录和检查器源码逐类扫描后，又发现一批**同构的子代问题**。它们此前没暴露，只是因为这次运行的 7 页内容恰好没踩到。

### 5.1 隐藏几何的完整清单（根因 2 的子代）

第一轮只列了 4 个高频项，扫描后盲区完整形态如下：

| 隐藏值 | 位置 | 后果 |
|---|---|---|
| `phone max-height:104cqw` | seed L96 | 区域给得再多，壳也封顶——想放大主体时无路可走，且这个上限无任何文档 |
| `bars .row height:20cqw` | seed L157 | 柱状图高度写死，多柱/单柱同一高度，区域再高也不放大 |
| `ldr .n min-width:14cqw` | seed L152 | 大数字强制占 14cqw，指标名长时被挤压——04 页账行问题的近亲 |
| `cr .k min-width:12cqw` | seed L126 | 标签条目左侧隐性占位 |
| `step .num width:7cqw` | seed L148 | 步骤序号列宽固定 |
| `timeline padding-left:6.9cqw` | seed L72 | 时间线整体左移 6.9cqw，与普通区域视觉宽度不同 |
| `.stagger max-width:94%` | seed L56 | 交错布局对每个组件隐性收窄 6% |
| `mn.lead padding-right:8.4cqw` | seed L184 | 引线旁注右侧隐性预留，混排时挤压同区组件 |

📌 结论升级：隐藏几何不是"几个遗漏项"，而是**种子的普遍状态**——组件的布局参数系统性写在 CSS 里、语义层一律不可见。所以解法也必须是系统性的（几何参数进目录，或预检工具），逐个登记只是止血。

### 5.2 软要求无拦截（与历史最严重缺陷 S1 同类）

- **`.region.bleed` 的"出血区域必须配一处标题或说明文字"没有任何 gate 规则检查**（已核对 lint-dom.mjs / validate.mjs 全部规则）。整页只剩图也能 passed——R12 只查"正文有可见组件"，`shot` 本身就算可见组件。这与当年最严重的 S1（正文整棵隐藏仍 passed）是同一性质：**文档承诺了、代码没做到**。区别只在触发条件更苛刻，但缺口是真实存在的检查器契约漏洞。
  - **【2026-11-12 已闭合】**：新增静态规则 **L23**（lint-dom.mjs）——区域挂 `.bleed` 时，head 或 bottom 至少要有一个可见文字叶；出血区内部图注不作数。出血本身仍然合法（封面手机出血、画面页出血不受影响），拦的只是"整页只剩图"。负例成对探针：`bleed-region-without-caption`（拒）/ `bleed-region-head-caption` 与 `bleed-region-bottom-caption`（对照放行）。同批加固：`layouts: null` 原会以 TypeError 崩溃，现归入"空对象"报错（project.mjs）。
- `.cover-bleed` 要求"手机根声明 `data-bleed` 并省页码"——`data-bleed` 只参与越界豁免的几何检查；**漏声明或忘省页码只会以 R2 遮挡的形式在渲染层撞出来**，反馈又走一遍全量重跑。这两条都是"约定写在文档里、验证推给渲染"的同类缺陷。

### 5.3 变体游离在 form 机制之外（ck 勾选态问题的根）

`form` 形态要求机制**只给 serif 注册了 shapes**。但组件实际有大量直接改变布局行为的变体根本没进这个机制：

| 组件 | 未登记变体 | 布局影响 |
|---|---|---|
| `shot` | `natural` / `fill` / `inset` | 三种裁切行为，空间占用完全不同 |
| `ck` | `done` | 勾选/空框，语义向读者承诺不同 |
| `mn` | `lead` | 引线版右侧隐性预留 8.4cqw |
| `ba` | `before` / `after` | 删除线/强调色，视觉重量不同 |

配方无法点名要求它们，计划也无法记录选择了它们。02 页"复选框没勾上"之所以无从判断是刻意还是遗漏，根源在这里——**变体选择既不受约束、也不留痕迹**。02 目检问题只是这个缺口的一个切面。

### 5.4 配对先验缺失的另外两处（根因 4 的子代）

- `mn.lead` 的引线"指向同区的画面"——目录一句话，**没有任何机制保证同区真的有画面**。引线指向空气也是合法页。配对约束（旁注↔画面）与 allow 白名单是两种粒度的约束，后者替代不了前者。
- P02（功能分栏）的 `require` 是 `[["fcard","frow","phone"]]`——三选一即可，**纯文字的功能分栏页也合法**。功能页没有任何视觉证据，与 P07 结尾页空同源：require 只设下限，不设"页面可读性"的构成要求。

### 5.5 脆弱耦合（无检查保证的数学前提）

- `--bleed-edge`（12.4cqw）的数值依赖"页脚单行"这个前提，种子注释自己承认"页脚多行需要重测该值"——**但没有任何检查保证页脚单行**。一旦署名文案长到折行，所有向下出血的数学全部错位，且错误在渲染层才暴露。这是隐藏几何的又一变体：连"种子自己写死的数值"都建立在一个未验证的前提上。
- `.quote` 默认档与 `hero` 档的适用边界只写在组件目录描述里（软话）。配方 P08 的 form 拦的是"金句页必须有 hero/marked/split"，**拦不住其他页擅自用 hero**——这次 P06 步骤流页若用了 hero 也一路绿灯（本次恰好没用）。

### 5.6 校验分级带来的静默弱化

多来源锚点（一个 `data-from` 挂多个资产）直接降级为 L16 告警并按"并集"语义比对——**挂两个来源就能稀释单源的逐字校验**。本次 p02 转场句 `data-from="h7 k9"` 就是实例：合法，但它是绕开严检的低阻力通道。逐字比对（L15）与并集告警（L16）的边界由"锚点数量"这个非语义因素决定，LLM 写多来源不承担任何额外成本，却换来宽松得多的校验。

### 5.7 补充排查的结论

四个根因不是全貌，它们各有"子代问题"散布在种子、目录与检查器三层。其中优先级最高的是 **5.2 的 `.region.bleed` 配文缺口**——它是当前唯一确认的"文档承诺 vs 代码事实"分离点，与历史上最严重的 S1 同类，应随下一轮负例套件补探针；其次是 5.3（变体入 form/计划），它是目检"无从判断刻意还是遗漏"的公共根源。

## 6. 结语

这次运行最有价值的发现不是"哪一页没做好"，而是**质量问题和耗时问题在同一个根因上交汇**：自由度给了，支撑自由度的信息没给。所有返修都在为"盲决策"付费，所有目检发现的搭配问题都是"无先验组合"的自然结果。改进不需要推翻架构——自然流、白名单、渲染后验证三条原则都值得保留——需要的是把信息流补齐：**让决策者在决策时看到决策的后果。**
