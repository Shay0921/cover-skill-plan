### 1.1 拓扑方案的真正死因：不是模板思想错了，是约束没有单一所有权

拓扑方案的形态与 FPR 高度相似（整页骨架 + 区域骨架 + 在组件使用处就地写行数/宽度限制）。它死于一个执行层缺陷：

> **同一个约束（如"条数"或"宽度"）同时存在于四层**：组件层限一份、配方层限一份、全局限制层限一份、最终检查层又限一份。
> 后果：改一层其余三层不动即互相矛盾；漂移发生时无法定位该修哪层；每修一轮都要对齐四份——这就是"优化和处理不完"的机制根源。

**关键澄清（本次最重要的历史修正）**：拓扑方案的失败与"模板/配方"思想本身无关。FPR 同样在配方里就地写限制（且只有配方一层写），却做到了高成品率。**死因是"单一所有权"缺失，不是"就地规则"本身。** 这直接决定了本次收敛方案的设计（§5）。

### 1.2 钟摆规律（六次摆动后的元观察）

每次换架构都是在修上一步的失败模式，同时引入自己的新漂移：

- JSON 契约：确定性最高 → 表达力为零
- 自由盲写：表达力最高 → 漂移无界
- 拓扑（模板思想）：漂移有界 → 死于执行层的四层重复
- 动态编排 + gate：几何漂移被治住 → **正向先验缺失**（内容轴零规格 + 页级组装自由）

**元规律：自由度是漂移的影子。** 消灭漂移只有两条路：消灭决策空间（模板/配方绑定），或提高驱动者纪律（流程强制 + 高成本循环）。自由组装的失败模式是**开放集**——件数、强调、档位、位置、密度，永远有新轴要新规则管，43 条 L/R 规则就是五个版本积累的账单；模板的失败模式是**封闭集**——基本只剩"内容塞不塞得进"，一个溢出检查兜底。**只要保留页级组装自由，规则就会永远加下去；这不是执行问题，是决策本身的代价结构。**

### 2.1 四个支柱

| 支柱 | 内容 | 实测证据 |

### 2.2 它为什么成品率高（三个被纠正的认知）

| 常见误读 | 实际机制 |

| "他让 AI 动态生成 HTML" | 明文"**不要从零开始写 HTML**"；AI 的工作 = 选配方 → 复制骨架 → 换文字。所谓动态只是每页选不同配方 |

## 3. 现行系统的病根诊断（本次失败的完整归因）

### 3.1 症状二分法

| 症状 | gate 能拦吗 | 病因归类 |
|---|---|---|
| fcard/list/ck 条数不对 | ❌ 拦不了（合法） | **正向先验缺失** |
| 高亮只有封面有 | ❌ 拦不了（合法） | 正向先验缺失 |
| 文字档位跨页漂移 | ❌ 拦不了（合法） | 正向先验缺失 |
| 标题位置随意 | ⚠️ 骨架档 R14 本该拦 | **疑似未走流程** |

| 位置不对 | ✅ R 系规则专门拦 | 疑似未走流程 |

对照证据：豆仓真实素材运行 7 页中 5 页被 gate 硬拦打回——流程走全时 gate 有效；47 页画廊全绿是作者级 agent 按完整流程跑的。**结论：症状分裂为两类病——"驱动纪律"（未走全流程）与"正向先验缺失"（走了流程也产出合法但难看的图）。两者都指向同一个根因 ↓**

### 3.2 五个病根

1. **页级组装自由度 = 漂移源**。骨架档只给数值区间（tracks 百分比），页 HTML 仍是 AI 每页现搭。FPR 在页级是预装配的（配方 = 整页骨架），我们的自由度比它大一个数量级。
2. **正向先验缺失**。内容轴零规格增长原则下，counts 只锁几何载体（7 档全在 phone/shot/step/bars），fcard/list/ck 件数为 0 约束；hl 分布、文字档位只有全局散文里的"可以"（许可），没有"通常应该"（先验）。**"可以多条"和"通常成组"对 LLM 是两种信息——许可不改变最小阻力路径。**
3. **require "至少 1" 是最小合法解的锚**。P02 要求 `fcard/frow/phone 至少其一`，最便宜合法答案是恰好 1 张——机制本身在把 agent 往"刚好满足"上引。
4. **约束跨层残留重复**（拓扑方案的遗产）：组件实例、配方 allow、全局规则、gate 检查多处管相近事务，新约束不知该放哪层，放哪层都和已有层打架。
5. **校验前置 + 驱动者不纪律 = 成本爆炸**。38 分钟/6 页的解剖：时间花在逐页"截图→看图→修"循环上。系统已有降耗杠杆（lint 一次报全、`--incremental`、geometry-digest）但依赖驱动者合规；而 FPR 的排序（渲染→看图→可选批查）从流程结构上消除了这个循环。

### 3.3 曾提出的引导级修复（已被架构级方案覆盖，留档备查）

曾拟定五处散文/示例引导（fcard description 去"一组"歧义、成组先验、hl 分布强化、intent 留痕件数、list 先验），后经"件数跟区域角色走，不跟组件走"修正（不同区域/骨架档的合理条数不同——封面左列 3-6 张与收尾单卡都合法，全局"成组是常态"会变成反方向偏见）。**该方案治标（引导先验），不治本（页级组装自由）；若最终保留现行架构可恢复执行，若走收敛方案则被配方绑定覆盖。**

**失败清单（静态证据）**：

| # | 症状 | 证据 | 病根归属 |

**六条教训**：

1. **预览需求真实且反复出现**：画廊翻车 → HANDOFF 否决预览模式（"非目标"）→ 用户再次要求 → 本次生成器。裁决压不住需求，agent 会持续在流程外即兴满足它。
2. **收敛方案的直接收益**：配方绑定骨架（骨架级配方 = 完整 HTML）之下，"26 档位预览"就是**配方库本身的渲染**——用户反复要的东西变成架构的自然产物，而非流程外即兴。
3. **即使有纪律的生成器也会在先验缺席处漂移**：hl / muted 的失败不在执行，在库——构造器把作者偏见复制 26 次。构图决策必须住库（配方），不住每次运行的代码。
4. **几何权威必须单一**：内联样式覆盖层 = 四层重复病的缩影（种子 CSS / 档位 carriers / 生成器内联三方争权）。"单一所有权"分层（§5.1 第二刀）直接治此。
5. **来源对账离开 pool/plan 管线就是装饰**：data-from 标记语法全对、语义全空。反编造链是**流程属性**，不是标记属性——这也是"三件套 + gate 不能省"的实证。
6. **自发架构指向收敛方向**：面对"26 档位"，agent 没有盲写而是造了参数化骨架系统——正是 FPR 思路。其失败恰好全部发生在即兴架构缺少"配方级规格"的地方（强调、档位、几何数）。本次运行近乎一次证明收敛方向的自然实验。

- **耗时**：本次生成器模式运行耗时 **49 分钟**——预览需求的即兴满足是昂贵的；第三次出现（画廊 → 首次预览 → 本次），每次都是流程外重造

**生成过程日志分析（第三轮取证，用户提供 49 分钟完整操作记录）**：

49 分钟 = 四轮"生成→渲染→看图→修"循环 + 2 次视觉误报复核。四个新发现：

1. **条件耦合约束缺失（新病根）**：agent 在返修中自行推导出"标题 2 行 → 正文可用高 ~891px → 手机 maxW ≤34cqw 才安全"的规则——**这正是骨架档本该前置提供的知识**。recipes.json 编码了 tracks/carriers 区间，但没编码"标题行数 ↔ 载体上限"的条件耦合，agent 只能渲染→被裁→测量→推导，四轮返修全是盲写学费重修（11-11 根因 2 原样重演）。FPR 整页骨架把这对耦合预烘焙进固定关系，运行期无需推导。**改造清单需含：骨架级配方必须显式登记标题行数与载体的耦合约束（或由整页骨架天然承载）**
2. **种子被运行期修改（数值所有权违规实证）**：为修 P07-B 单页溢出，agent 改了共享种子的全局数值（`.bars .row` 20→14cqw、ldr/ledger padding），理由"对其他地方也安全"——实际所有用到这三个组件的页面被静默改了密度。种子是唯一数值源，恰恰因此改一处动全身；agent 利用这点做局部修复。正确修法是内容级（减行）或档位级（换骨架）。**"单一所有权"必须配执行面：种子数值只许设计期人审修改，运行期禁改（gate 校验种子完整性/校验和）**
3. **逐调用魔数 = 第五几何权威**：39/35/34/42 全是经验推导值，与档位 carriers 区间（40-42）矛盾但"看起来成功"——契约外数字必然漂移的又一次实证
4. **正面记录（如实）**：agent 工程素质高（系统 grep 风险点、视觉误报二次复核、b64 上一轮损坏本轮修复）；全程自标"预览非正式出图"。**元结论：agent 越能干越会自建体系绕过流程——它的失败不是能力问题，是架构迫使它重新推导库里该有的知识、用全局改动修局部问题。流程必须在"好用"上与自建体系竞争，否则必被能干的 agent 规避**

## 4. 颗粒度裁决（配方粒度的核心决策）

本次讨论定下的设计词汇与边界：

### 4.1 归属表：什么进组件，什么进配方

| 判断标准 | 归属 | 示例 |
|---|---|---|
| "是什么"（内部几何） | **组件类**（种子 CSS 锁死） | 一张卡 = 标题+说明+图标位 |
| "在哪个页面、几条、多大、跟谁排"（外部语境） | **配方**（设计期写死） | 左 fcard×3-6 右 phone 是"卖点页"配方 |
| 内部几何相同、仅位置/条数/搭配不同 | 同一组件类，**不同配方** | fcard 伴机 vs fcard 收尾 |
| 内部结构本身不同 | 配方里**独立 markup**（可复用基类+修饰符） | 参照 FPR 的 M07（收尾行）对 M08（账本行）两套规格 |
| 镜像/翻转 | **不是新配方**——锁死方向或登记显式变体 | 手机左 vs 手机右 |

### 4.2 语义匹配发生在选配方时，不在写页面时

```
内容语义 → 挑配方（intent 匹配，语义重合的那条是对的）→ 配方已绑定组件+条数+排布 → AI 只换文字
```

- 并列卖点/功能/收益 → 卖点页 → 左栏自然是 fcard×3-6，无需再想
- 待办/勾选/条件核对 → 清单页 → 左栏自然是 ck×N
- 时序步骤 → 流水线页 → 左栏自然是 step

**不拆组件适配语境**——组件一拆多，"什么时候用哪个"又成为新的漂移轴，CSS 与实例维护翻倍，等于把四层重复痛苦换个方向请回来。

### 4.3 配方命名按内容语义，不按画面特征

| 现在 | 收敛后 |
|---|---|
| 12 条配方，命名按画面（"功能分栏页"），槽位 = allow 白名单（多选） | ~20 条配方，命名按**读者体验**（"并列卖点页""任务清单页""步骤流程页"），槽位 = 绑死组件 + 条数区间 + 排布 |
| AI 每页决定：选组件、几条、怎么排 | AI 只决定：这条内容属于哪条配方 + 换文字 |

配方带 `intent` 字段的机制已存在（01-content-refinement："配方按 intent 选，语义重合的那条是对的"），语义匹配的基础设施不用新建。

### 4.4 配方供给分级（从 FPR 学到的关键细化）

不是所有配方都值得给整页 HTML：

| 级别 | 判据 | 供给物 | 来源 |
|---|---|---|---|
| **骨架级** | 结构复杂、部件多、历史上易漂移（封面 fcard 伴机、数据账本、时间线、对比、矩阵页） | 整页可复制 HTML | **47 页画廊就是现成的源**（全部过 gate、已被用户目检认可），从中提炼 |
| **规格级** | 部件少、结构简单（金句页、收尾页） | 精确结构要点 + 条数区间 + 密度下限 + 必需锚点 | 参照 FPR 的 18 个规格级配方写法 |

## 5. 收敛方案（完整设计）

**方向：向 FPR 架构收敛，但不是退回旧拓扑——是"FPR 的架构 + 本系统的来源链"。**

### 5.1 三刀手术

**第一刀：配方升级为读者体验绑定制**
- 配方按读者体验细分（12 → ~20 条），每条配方的槽位绑死：组件 + 条数区间 + 排布 + 密度规格
- 骨架级配方给整页 HTML（从 47 页画廊提炼）；规格级配方给就地规格
- 现行"骨架档"角色并入配方（几何规格或整页骨架），不再独立存在
- 允许集（allow）从"多选菜单"变成"基本唯一"；require 下限语义随之消亡（组件已绑定，无"至少 1"可锚）

**第二刀：约束单一所有权分层**（拓扑方案死因的直接解药）

| 层 | 唯一职责 | 禁止越界 |
|---|---|---|
| 配方 | 构图决策：组件、条数、排布、密度、锚点 | 不写 CSS 数值 |
| 种子 CSS | 所有数值：尺寸、间距、字号、响应式 | 不含示例 markup 之外的结构决策 |
| gate（瘦身） | **只查后果**：溢出、碰撞、密度、最小字号、来源对账 | 不重复验收配方已锁定的决策（条数/排布不再进检查器） |
| 计划（pool/plan） | 内容取舍、来源对账（data/quotes 逐字） | 不记布局 |

任何新约束入册前先回答：**"已有哪些层在管这件事？"**——答案不是"没有"，就不许再写一份。

**第三刀：校验后置批量化**
- 流程改为：生成 → 渲染 → 先看图 → 需要才跑批查 → 修 FAIL → 交付
- gate 从"交付前验收者"降为"后果兜底 + 来源对账"；保留几何硬校验（这是 FPR 没有的防线，不删）
- 治 38 分钟：消除逐页循环的结构诱因

### 5.2 保留资产清单（不可丢）

| 资产 | 为什么保留 | FPR 有没有 |
|---|---|---|
| pool/uses 来源对账链 + data/quotes 逐字校验 | 反编造刚需（产品卡片不能编数字） | ❌ 没有（AI 编"132K"无人拦） |
| 几何硬校验（溢出/遮挡/越界） | 后果兜底 | ⚠️ 有但更弱（9 条 vs 我们 R 系） |
| 26 组件库 + shapes 变体 | 组件级几何的执行源 | ✅ 同构（他的类定义体系） |
| 种子 CSS（cqw 单位体系） | 数值唯一源 | ✅ 同构 |
| 47 页画廊 | 骨架级配方的提炼源 | —— |
| 183 条负例 | gate 瘦身时的回归基准 | —— |

### 5.3 明确不做

- ❌ 不拆组件适配语境（见 §4.2）
- ❌ 不把内容组件 counts 塞进加载期注册表（架构拒绝内容模板化；条数住配方，不住检查器）
- ❌ 不做占位预览模式（HANDOFF 已裁决，继续有效）
- ❌ 不恢复五处引导级修复（被配方绑定覆盖；若最终不收敛再回档 §3.3）
- ❌ 全部配方无差别上整页骨架（成本失控；按 §4.4 分级）

### 5.4 验收判据（怎么算成了——预注册，防摆锤）

六段钟摆的元缺陷之一：每次摆动都没有事先写死成功标准，导致每次跑完都凭感觉再摆一次。本方案的判据提前注册：

| # | 判据 | 达标线 |
|---|---|---|
| 1 | **症状清单消失** | 同一真实素材、同级别驱动 agent：fcard/list/ck 条数合理、标题位置稳定、hl 逐页分布、金句页留白——上一轮 §0 症状清单逐项不复现 |
| 2 | **耗时收敛** | 单组交付 = 生成 + 一轮看图 + 至多一轮批查；不再出现逐页"截图→看图→修"循环（对照本次 38 分钟/6 页） |
| 3 | **回归不破** | 来源对账链（pool/uses/quotes 逐字）保持全过；几何后果检查（溢出/碰撞）仍能拦住注入的坏页 |
| 4 | **防摆锤条款** | 收敛架构跑完上述判据后，若结果未达标——修的是**配方内容**（规格/骨架细节），不重开架构争论；除非连续两轮素材上判据 1 系统性失败 |

### 5.5 代价（如实记录）

- **上限明确**：收敛后的天花板即 FPR 的天花板——用户实测其成品后评价"不满意"。变体丰富度靠配方数量（~20）与组件 shapes 变体弥补，低于自由组装的理论上限
- **配方数量翻倍**：12 → ~20 条，设计期工作量增加（但画廊提供骨架源，且一次性成本）
- **原始意图修订**：HANDOFF §1 锚点"AI 从组件中选择不同的组件进行排版"需修订为"**AI 选配方排版；组件选择收敛进配方设计期**"。这不是意图被推翻，是用户在真实失败后主动重估："我不排除那种方法是错的……我现在只是希望选择一个更好的方法。"（2026-11-12 原话）

## 8. 一段话总结（给未来的接手者）

六次钟摆的答案从来不在"哪套架构更先进"，而在两个变量：**决策空间给多少**（自由组装 = 开放集账单，配方绑定 = 封闭集账单）和**约束住在哪层**（单一所有权 = 可维护，四层重复 = 改不完）。本次失败不是第 5 段架构的执行失败，而是它付费购买的那份自由（页级组装 + 内容轴零规格）在真实使用中交出了账单。收敛方案的本质：把 FPR 用实践验证过的账单结构（页级预装配 + 决策点就地规格 + 单层所有权 + 校验后置）移植过来，同时保留本系统比它强的地方（来源对账链 + 几何硬校验）。上限换成品率，一笔明确的交易——是否成交，由用户拍板。

## 9. 附录：收敛形态示例（示意，非实现）

> **本附录地位**：把 §5 三刀落到"可想象的具体形态"，服务架构拍板。全部为**示意**，不代表已实现；实际实现以拍板后的改造清单为准。示例沿用现行系统真实资产命名（fcard / phone / hl / data-from / pool / 骨架档等），便于对照。**本附录不构成执行授权。**

### 9.1 骨架级配方样例（第一刀 + 条件耦合预烘焙）

配方登记卡（示意）：

```
配方 R-SELL-01 · 并列卖点页（骨架级）
├─ intent：并列卖点 / 功能 / 收益的展示页；读者扫一眼能数出"有 N 个卖点"
├─ 绑定：左列 fcard × 3-6（成组、等高、间距走种子 .stagger）+ 右侧 phone（锁高满列）
├─ 供给物：整页可复制 HTML（从 47 页画廊提炼，登记源页号；须过 gate 实证）
├─ 预烘焙耦合：标题 ≤2 行 → 左列可用高固定 → fcard 最多 6 条；
│   标题 3 行 → fcard 最多 4 条。关系由整页骨架结构天然承载，运行期零推导
├─ hl 先验：3-6 张中恰好 1 张带 hl（强调节奏）；禁全 hl、禁全无
└─ 对账：每张 fcard 的标题/说明/图标字逐字段登记 data-from
```

对应整页骨架（示意片段）：

```html
<!-- 配方 R-SELL-01 · 并列卖点页（骨架级，提炼自画廊 #页号） -->
<section class="poster">
  <header class="ph"><!-- 标题 ≤2 行，结构固定 --></header>
  <div class="cols-2">
    <div class="stack">
      <!-- fcard × 3-6，结构固定只换文字；hl 恰好一张 -->
      <div class="fcard [is-hl]" data-from="卖点标题字段">…</div>
    </div>
    <div class="phone"><img src="assets/iphone-frame.png" alt=""></div>
  </div>
  <footer class="pf">…</footer>
</section>
```

📌 **关键点**：AI 的工作 = 判断"这是并列卖点页" → 复制整页 → 换文字。条数区间、hl 节奏、标题行数↔手机的耦合（§3.4 第三轮取证病根 1）、全部几何——不需要任何运行期决策。49 分钟日志里 agent 用四轮返修自推导的那条规则，在这里是骨架自带的。

### 9.2 规格级配方样例（金句页）

配方登记卡（示意）：

```
配方 R-QUOTE-01 · 金句页（规格级）
├─ intent：单句主张 / 情绪峰值 / 转场页
├─ 硬规格：
│   ├─ 画布占比 ≤60%（全库唯一允许大面积留白的配方）
│   ├─ 必需锚点三件：serif 金句（quote.hero）+ 出处行 + 一个视觉锚（印章/编号）
│   ├─ 密度上限：正文区不得出现清单或多段文字
│   └─ 给不出三锚点 → 不许用本配方，降级为引言页（防"满篇文字金句页"复发）
├─ hl：serif 句内恰 1 处
└─ 供给物：仅结构要点（如上），不给整页 HTML
```

📌 **为何不给整页 HTML**：结构太简单，整页骨架反而鼓励逐字复制、跳过内容取舍。这与 §4.4 分级判据（部件少 → 规格级）一致。

### 9.3 完整新流程走查（第三刀，端到端）

以一条真实 PRD 内容"产品支持 3 种导出格式"为例：

1. **提炼**：文案进 pool（data-from: PRD §4.2），定这页讲什么
2. **选配方**：内容语义 = 并列卖点 → 命中 R-SELL-01（不决定组件、条数、排布）
3. **生成**：复制骨架 → 换文字 → 3 张 fcard 各登记 data-from
4. **渲染**：出 PNG
5. **看图**：**先给用户看**（此时不打分、不拦截）
6. **可选批查**：用户要求才跑 gate（来源对账逐字 + 几何后果）→ FAIL 才修
7. **交付**

与现行流程的差异：步骤 2-3 现在要"查骨架档 → 查 counts → 查 allow → 现搭 HTML → 查全局散文"五个决策点，收敛为一个"选配方"；步骤 5-6 顺序反转，从流程结构上消除逐页"截图→看图→修"循环（38 分钟病）。

### 9.4 待展开项登记（改造清单阶段展开——固化当前思考，防丢失）
