## 0. 一句话目标

把现行"契约 JSON + 骨架档 + 页级自由组装"改造为"**读者体验绑定制配方库（骨架级给整页 HTML / 规格级给就地规格）+ 约束单一所有权 + 校验后置批量化**"，同时保留本系统的来源对账链（pool/uses/data-from/quotes 逐字）与几何硬校验。

改造后的运行期心智模型（给未来实现者的北极星）：

```
内容语义 → 选配方（intent 匹配）→ 复制骨架/按规格组装 → 只换文字与槽位
        → 渲染 → 先给用户看 → （用户要求才）批查 gate → 交付
```

AI 不再决定：组件选谁、条数几条、怎么排、多宽——这些全部在配方设计期锁死。

### 4.1 阶段 0 盘点字段（数据字典）

| 字段 | 取值来源 | 说明 |
|---|---|---|

### 4.2 聚类判据（MILESTONE §4.1 归属表的操作化）

两页归并为同一配方，当且仅当：

1. **读者体验同构**：读者扫一眼获得的"这一页在讲什么结构"相同（并列 N 个卖点 / 逐步流程 / 单句主张 / 账目对照…）——命名按此，不按组件
2. **构图决策同构**：组件选择、条数区间、排布关系、锚点数量一致；仅文字与截图内容不同
3. 不满足 1/2 但仅方向/左右相反 → 同配方**变体**（variants 字段登记），不另立
4. 内部几何相同但"在哪、几条、多大"不同 → **不同配方**（fcard 伴机 vs fcard 收尾是两条）
5. 单实例配方（P06/P10）裁决顺序：先试归并进已有读者体验 → 不合脚再独立成配方 → 仍单实例且结构简单则降为规格级

### 4.5 gate 瘦身处置流程（阶段 3 的操作顺序）

1. 列全 43 条 L/R 规则（来源：gate 规则表 + 骨架档 L 系 + 构图不变量 R 系）
2. 逐条标分类：迁移 / 保留 / 砍（判据：这条规则验收的是"配方已锁死的决策"还是"后果"？前者迁移或砍，后者保留）
3. **每砍/迁一条 → 跑一次 183 负例全量**（`negative-index.json`）→ 该规则对应的坏例子集必须仍全 FAIL（被后果检查拦住）
4. 拦不住的 → 该规则改写为后果检查（不是恢复原规则）
5. 最终状态：gate = 后果检查（溢出/碰撞/密度/最小字号）+ 来源对账（逐字）+ 种子/资产完整性；**不含任何条数/排布/组件选择类检查**

- 这是对 49 分钟日志病根 2（`.bars .row` 20→14cqw 静默改全局密度）的结构性封堵
