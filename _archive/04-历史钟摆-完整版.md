## 1. 第六方案（配方收敛）的完整因果链——为什么它成功了，又被弃用了

**它达成了当初承诺的一切**：47 页用户认可的画廊 → 蒸馏 20 条配方 × 41 个骨架档；41/41 真实回归零错误；约束单一所有权砍掉四层重复；三把只读锁；184 条负例回归网；11-11 症状清单零复发。技术上是成功的一代。

**它被弃用的三个原因（全部来自 2026-11-13~15 与用户的对账）**：

1. **词义漂移事故**：11-12 当天"配方"一词被换了语义（旧：白名单多选+AI 动态组装；新：绑死组件+冻结页）——用户记忆中的"20 个配方动态组成"是旧语义，方案文档用同一词承载新语义且未显著声明，误会潜伏三日爆发。
2. **运行时复杂度**：填字期契约（池/计划/data-from 对账）+ gate + 锁 + 184 负例，是为"不可信驱动 agent"配的保险层；用户实际工作流是"自己出图、发布前人审"，保险层对他是纯开销。
3. **绕路实证**：收敛方案的运行时（选档→复制→填字）与用户 10-21 的手写母版库同构——第六方案绕了三周回到 0 号方案的形状，却携带了 0 号不需要的机器保险。

**第六方案的遗产（全部保留）**：

- `seed/` + `references/recipes/` 41 档 + 字体 + 手机框 = **纸质杂志风风格库**（第二风格库整体存活）；
- `data-layer/data-editable/data-slot` 标记体系 = **与 pageApp 编辑器契约（v1.9）同源**，平移进新母版规范；
- 填字纪律知识（字数/密度/hl/图片形状）= 蒸馏进 final/01 手册 §3.5/§3.6；
- cdp/find-chrome 渲染管线 = render.mjs 的地基；
- "槽边就地写限制"的思想源头（FPR 分析）= 新母版的头部注释规范。

**第六方案正式废弃的机器（2026-11-15 判定）**：三把只读锁、184 负例套件、来源对账链（pool/plan/data-from 逐字）、检查器全套（L/R 系）、config 双 json——全部随路线退役，处置见 [05-资产对账与操作清单.md](05-资产对账与操作清单.md)。

## 2. 第七方案（固定母版制）确立记录

**拍板过程**（2026-11-13~15 五轮对话）：用户连续质疑（41 母版≠动态→复制源争议→组件 json 冗余→"动态只在开发期"→"我为何需要 AI 生成母版"）→ 监工逐层认账（配方换义、复制源落差、h68 类资产判定）→ 用户出示 coverDemo 四代库实物 → 确认编辑器 pageApp 已建成且契约完备 → 拍板整体转固定母版制，T14（第六方案的真实素材验收）废弃。

**新架构一句话**：版式由人定死（每风格 `style.css` + `templates.html` 平铺 20-40 母版），AI 只做语义选择与内容填入（plan.json），render.mjs 负责抽取/填槽/克隆/截图并产出 pageApp 编辑器契约的交付物，机器检查退役、只留三项防呆（`{{` 残留/图片缺失/画布确认），质量由"槽边限制 + 人眼 + 编辑器终审"承担。

**为什么这次不是第八次摆锤**：摆锤=抛弃上一方案引入新漂移；本次是**归位**——回到用户 0 号原点的形态，没有新增任何运行期自由度，唯一的"新"是把 0 号方案缺的三件事补齐（语义选择目录、脚本出图、编辑器契约）。防摆锤条款的本意（不凭感觉重摆）继续适用于本方案。

**开放决策点（沿用手动清单）**：h75 card02 弹性化、P8 机制化、config 去重等第六方案挂账随路线一并注销——若纸质风库激活且遇到同类问题，从 archive 取回诊断文档重开。
