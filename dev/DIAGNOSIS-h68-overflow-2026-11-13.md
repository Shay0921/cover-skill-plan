# h68 骨架溢出 · 诊断结论（2026-11-13）

> 性质：诊断归档，非修复。本文不修改任何种子/配置/骨架/gate。
> 上游：`dev/e2-duo-h68-1113/work/qa-report.json`（R1×6 实锤）、T7-GATE §六、constraint-ownership-map。
> 用途：阶段 A（h68 溢出修复）与阶段 B（宽度档镜像债）的唯一决策依据。

---

## 0. 一句话结论

`phone01-duo-labeled`（源页 43）的手机是**固定高度档 h68 = 68cqw ≈ 734px**，而它所在的 wall 区高度是**动态的**（随 head 区文案长度波动）。当 head 文案变长，wall 被压到 < 781px 时，手机 + 下方标签（合计 781px）就越出 wall 区，触发 gate R1。这不是 gate 误报，是真实的几何溢出。

---

## 1. 完整事实链（全部实测）

### 1.1 坐标系与关键常数

| 项 | 值 | 来源 |
|---|---|---|
| 画布 | 1080×1440px | R0 校验 |
| 1cqw | 1080 ÷ 100 = 10.8px | validate.mjs L72 |
| 手机壳 `iphone-frame.png` | 910×1806，宽高比 0.5039 | sips 实测 |
| 手机截图占比 | 高 92.30%、宽 84.73%（壳自带上下边框各约 28px） | seed L104 |

### 1.2 手机档位（seed `paper-journal.html`）

| 档位 | 高度 | 宽度（= 高度 × 0.5039） | 定义位置 |
|---|---|---|---|
| 无档位（默认） | `height:100%`，上限 `max-height:104cqw`，下限 `min-height:48cqw` | 随容器 | seed L97 |
| **h68** | 68cqw = **734.4px** | 34.27cqw | seed L99 |
| **h75** | 75cqw = **810px** | 37.79cqw | seed L100 |

### 1.3 duo-labeled 的垂直占位（源页 43 真实渲染）

| 层 | 高度 |
|---|---|
| 手机 `.phone.h68` | 734.4px |
| 手机到标签间距（`.phone-cell` gap） | 15.1px |
| 界面名标签 `.text-block` | 31.8px |
| **合计** | **781.3px** |

### 1.4 wall 区高度是动态的（实测两组干净渲染）

| 场景 | head 区高度 | wall 区高度 | 781px 是否塞得下 |
|---|---|---|---|
| p43 短文案 | 230.8px | **804.9px** | ✅ 塞得下，上下各留 23.6px |
| e2 长文案 | 252.4px | **749.7px** | ❌ 溢出 31.6px（上下各 15.8px） |

> ⚠️ 表内 e2 标「长文案」为早期口径：实际 e2 的 sub 仅 8 字、head 反而更高是字体未加载所致，修正见 §8.4。
>
> wall 高度 = 画布高 − head 区 − 页脚区，`.p-page` 用 `minmax(0,1fr)` 把剩余空间全给 wall。head 区高度随文案折行数浮动 → wall 跟着反向浮动。h68 是写死的，两者在赛跑。

### 1.5 e2 的 R1 报错原始模式

`overview-evidence 越出所属区域 wall`，sides 为 `{ top: true, bottom: true }`（双向越出）。溢出量约 16px，落在 wall 与 head/bottom 的 gap 里，不压文字、不出画布——所以 `dev/_sc` 预览（只量画布边界）和肉眼都看不出来。这就是 T7 早就写下的"预览 PASS ≠ gate PASS"。

## 2. 三文件存 h68 的镜像分析（本次新发现）

h68 这个几何事实，散在三处，性质不同：

| 位置 | 存什么 | 性质 |
|---|---|---|
| `seed/paper-journal.html` L99 | `.phone.h68{height:68cqw}` | **几何唯一真源** |
| `config/recipes.json` L52 | `carriers:[{component:"phone",region:"wall",width:[33,36]}]` | **派生镜像**（68×0.5039≈34.27 落在 [33,36] 正中） |
| `references/04-recipes.md` R-phone-01 登记卡 | "h68 档" | **人读规格说明书**，非几何事实 |

**真正的病灶只有前两处之间**：高度档（seed）与宽度档（config）是同一个几何事实的两个表达，宽度是高度乘手机壳宽高比算出来的，但两者**没有任何关联机制**——改 h68 高度，config 的宽度档不会自动跟着变，必须手工同步，漏一步就触发校验叠加冲突（R1 溢出 + R14 宽度档越界）。

这是 `constraint-ownership-map.md` C1~C6 反复在砍的"同一约束住多处"病灶的**几何版**：之前砍的是规则重复（allow/max/require/form/counts），这次是**高度↔宽度的镜像重复**。

## 3. 别的组件是否同病（本次新发现）

### 3.1 phone 固定档位：h75 同病，且更隐蔽

| 骨架 | 档位 | config 宽度档 | 是否镜像 |
|---|---|---|---|
| duo-labeled（源页 43） | h68 | [33,36] | ✅ 34.27 落正中 |
| card02-centered（源页 45） | h75 | [36,40] | ✅ 37.79 落正中 |
| note02-phone-dcards（源页 44） | h75 | [36,40] | ✅ 37.79 落正中 |

**h75 是一模一样的病**，而且 h75 = 810px，比 h68+标签（781px）**更需要高 wall 区，其实更接近翻车**。它现在没报 R1，纯粹因为源页 44/45 的 head 文案短、wall 够高。AI 一旦给它套长文案 head，h75 会先于 h68 溢出。

### 3.2 shot 载体：不同质，别混为一谈

`shot` 是 `height:100%` 吃满列高，宽度由列宽决定，所以 config 里 shot 的宽度档（[40,43][48,52][41,46][40,45][96,104]）是"防载体被压太窄"的**区间约束**，不是高度镜像。**镜像债只涉及带固定高度档的 phone（h68/h75），不涉及 shot。**

## 4. 已排除方案及理由

| 方案 | 为什么排除 |
|---|---|
| **gate 静默/警告（降级 WARN）** | 技术上可行且机制现成（`issue()` 支持 `level='WARN'`，R7/R9/FONT 已有先例，WARN 不计 FAILED）。但有三重代价：①不是"静默"而是"降级目检"，报告仍留记录；②两条降级路都伤架构——精准豁免（gate 认 h68）违背"gate 不含配方决策"，通用放软（R1 整体降 WARN）拆掉后果检查核心闸；③**溢出是真的不是误报**，降级=明知溢出却放过，与"零溢出交付"冲突 |
| **降档 h64** | 手机永久缩 5.9%（所有场景图片都变小，用户已确认不可接受）；且宽 32.25cqw < R14 阈值 32.5cqw，**会新触发 R14 越界**，反而引入第二个校验冲突 |
| **降档 h65** | 702px，宽 32.75cqw，仅余 2.7px 擦边，标签折两行仍溢出 |
| **head 极简条件** | 源页 43 是完整头部（kicker+h1+sub），不是极简头，条件不成立 |
| **去掉手机壳上下留白** | 那 56px 是 `iphone-frame.png` 自带的物理边框（刘海/圆角），去掉截图会顶穿壳、盖住圆角，穿帮 |

## 5. 剩余可选方案（阶段 A）

### 方案 A-1：弹性 + max68 上限（推荐）

> ⚠️ 本节为 2026-11-13 上午草案：施工方式已被 §8.1 定案取代（`:has` 方案，41 骨架零 diff，无「骨架换类」步骤）。

手机高度不写死，改成 flex 吃满 wall 区里"标签之外"的空间，封顶 `max-height:68cqw`。实测：

| 场景 | 现状 h68 | 降档 h64 | **弹性+max68** |
|---|---|---|---|
| 正常（wall 804.9） | 734.4px 不溢出 | 691.2px 永久小 5.9% | **734.4px 不变**（顶到上限） |
| 溢出（wall 749.7） | 734.4px 溢出 15.8px | 691.2px | **702.8px 自动缩 4.3%，零溢出** |

- 选择器用 `:has(.phone.h68)` 精准命中，**只动 p43 一个骨架**：trio（无档位）、card02/note02（h75）、card01 族、list01、step01、duo-cover 一像素都不动。
- 代价：p43 手机高度从"固定档位"变"随文案轻微浮动"（只此一处）。
- 需同步：改 seed 三处同步（含 SHA-256 校验和重算）→ 骨架换类 → 登记卡/映射表更新 → **顺带把 config 的 R14 宽度档从 [33,36] 拓宽到能覆盖浮动范围（如 [32,36]）** → `_sc` 43 重渲目检 → 真实管线复验销单。

### 方案 A-2：弹性方案 + 顺带把 h75 一起修

在 A-1 基础上，把 h75（card02/note02）也改成弹性 + max75。一次清掉两个 phone 固定档的溢出根因，但改动面更大（3 个骨架 + 2 个宽度档）。

## 8. 最终定案（可施工）

### 8.1 定案参数

| 项 | 定案值 |
|---|---|
| 方案 | 弹性 + `max-height:68cqw` 上限 + `min-height:63.5cqw` floor |
| seed `.phone.h68` | `height:68cqw` → `height:auto; flex:1 1 auto; min-height:63.5cqw; max-height:68cqw`（`aspect-ratio:910/1806` 保留，宽度由高度自动派生） |
| cell 拉伸 | 加一条 `:has()` 规则命中含 h68 的 `.phone-cell` 使其正确 stretch（具体 flex 组合施工时实测校准；`:has` 已核验 Chrome 105+/CDP 渲染链可行，且 h68 唯一消费者=duo-labeled，改 seed 单文件、41 骨架零 diff） |
| config 宽度档 | `R-phone-01.duo-labeled.carriers.width` [33,36] → **[32,36]** |
| 登记卡 | `references/04-recipes.md` R-phone-01 标注"h68 弹性档：max 68cqw / min 63.5cqw，触底即内容与配方不匹配，换配方或删文案" |
| 种子纪律 | 三处同步 + SHA-256 校验和重算（`dev/check-seed-lock.mjs` 复验） |

### 8.2 floor 语义（重要，防误读）

A-1 不是"零溢出"，是"**floor 之上零溢出**"。修好后正常文案不再触发 R1；只有 sub 折 3 行以上或字体加载失败使手机触底 63.5cqw，R1 才诚实触发——此时是"内容与配方不匹配"的真信号，走换配方/删文案的合法逃生口。与 seed L101-102 注释哲学（"区域给不出高度是布局问题，换区域而不是让壳缩下去"）同源。

### 8.3 验证闭环（五项，全过才算销单）

1. e2 h68 场景重跑真实管线 → R1×6 应清零；
2. p43 短文案场景重跑 → 手机仍 734.4px 顶格（证明正常态无回归）；
3. 178 负例全跑（R14 [33,36]→[32,36] 可能波及既有夹具预期，重对账）；
4. `_sc` 43 重渲目检 + 其余 42 张应零像素差（h68 只被 duo-labeled 使用）；
5. negative-index 补一条"h68+长文案"夹具锁死本次修复。

### 8.4 新发现：字体加载是溢出放大器（施工时顺带观察）

e2 的 sub（8 字）比 p43（24 字）短，head 区却高 21.6px——根因是 e2 渲染时 Playfair/Noto Serif 大量 unloaded、fallback 系统字体撑高 head。即 e2 的 wall=749.7px 是"字体未加载"的坏情况，真实字体正常时手机基本维持 68cqw、几乎不缩。故 floor 63.5 在真实环境触不到，属稳健下限；字体加载稳定性本身是独立观察项，不属本次修复范围。

### 8.5 阶段 B 备忘（另立项，不与 A 混）

方向：R14 宽度档从"手工写死镜像"改为"从 seed 档位自动派生（高度×0.5039）"或"直接校验档位高度"，消除 seed↔config 高度/宽度两处事实源；h75（card02-centered、note02-phone-dcards 的 [36,40]=75×0.5039≈37.79）溢出隐患一并解决。牵连 R14 校验实现 + config carriers 结构 + 所有带 carrier 配方，需完整重跑 178 负例。
