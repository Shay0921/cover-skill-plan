## 一、我的方案（一句话版）

三层 + 两个执行器：

1. **角色层（role）**：封面/清单/对比/金句/结尾… 是一层独立的语义包裹，只管"页码开不开、kicker 要不要、页脚/装饰风格"，**与布局无关**。这样 P01（封面）和 P04（清单）即便共用"左内容右手机"骨架，也能靠角色区分，不会撞车。
2. **骨架层（skeleton）**：只描述几何——单栏 / 两栏左内容右手机 / 图墙 / 时间线 / 对比块 / 出血大图。不绑具体内容。
3. **填充层（fill）**：从 recipe 的 `allow` 里选组件，把**数量 / 顺序 / 对齐 / 错位**做成生成时的参数，而不是冻成档位。
4. **执行器**：加载期 schema 守卫（你提的，封几何轴）+ 渲染期无头浏览器校验（guizang 的 R1–R9，封渲染轴）。

核心一句话：**把"角色"从"布局"里拆出来，把"组件选择"从"档位"里拆出来。**

## 二、guizang 是怎么做的（关键发现）

他**根本没有"档位/tier"这层**。结构是这样：

- **Non-Negotiables 写成规则不是枚举**："文字不得溢出/贴边/撞页脚""标题不得贴下一块""3:4 卡必须吃满画布，>15% 纯空白带需留白理由""溢出修复阶梯 1–40px 微调 / 40–90px 收紧 / 90–160px 压缩 / 160+ 换 recipe"。

## 四、你的"轴纪律守卫"方案——我的评价

**方案本身（加载期拒绝 `counts`/`carriers` 出现在内容组件上，白名单 {phone, shot, step, bars}）：**

✅ **它封死的是最危险的爆炸路径**。你担心的"给 fcard 加 counts → 派生 fcard-2/fcard-3/fcard-4 档"被物理拒绝，强制"组件数量"只能是生成期参数，不能是档位维度。这把"档只锁几何"从散文纪律变成机器检查，完全符合你"每个 must 要有执行器"的原则。

✅ **一个漂亮副作用**：如果"左栏用 fcard 还是 ck"也走 `carriers` 通道，守卫会因白名单拒绝 fcard/ck 作 carrier，从而**倒逼组件选择必须活在 `carriers` 之外的 fill 字段**——间接落实"组件选择 ≠ 几何档位"。

⚠️ **但它是"必要非充分"**，有三处要补：
1. **它只封几何轴，没封"组件选择轴"**。A vs C 的重复、以及"全用浮动卡"的偏见，源于"左栏选 fcard/ck/frow"仍是逐档手写——守卫拦不住这个。必须让组件选择成为生成参数（我的第 3 层 fill），而不只是不让它进 `counts`。
2. **白名单应是 schema 派生的，不是事后清单**。"今天实际用到的"是经验值，容易失同步。更干净的做法：在 schema 里把 `counts`/`carriers` 定义为**只存在于几何组件分支的字段**，而不是"先允许再事后拒绝"——守卫检查 `carriers[].component ∈ {phone,shot,step,bars}` 且 `counts` 的键同样受限。
3. **它不解决角色耦合，也不解决渲染校验**。封面 vs P04 撞车要角色层；出血/居中/留白/标题间距要 guizang 式渲染校验。守卫是几何轴执行器，另两个轴各需一个执行器。

## 五、结合后的"更好方法"（三个执行器）

把你、guizang、我的长处拼起来：

- **保留** cover-skill-plan 的 `allow/require/form`（机器可读约束，比 guizang 散文强）。
- **砍掉** 26 个冻住档位 → recipe 退化为**骨架 + 参数化填充**（guizang 的结构观：枚举到意图/结构层，不枚举组件组合）。
- **加载期守卫**（你的提案）= **几何轴执行器**：`counts`/`carriers` 只认 {phone,shot,step,bars}，组件数量/选择不得入侵档位。
- **渲染期校验**（guizang 的 R1–R9）= **渲染轴执行器**：溢出/页脚冲突/底部留白/标题间距/最小字号，直接 kill 我们整类"校验问题"。
- **角色层**（我的提案）= **语义轴执行器**：页码/kicker/页脚开关独立于骨架，解决"封面 vs 清单"撞车。

这样"增长线性"才真正成立：加一个新组件不用加档（几何守卫拦着），加一个新几何排列才加档（这是合理的枚举维度），加一个新角色只加一层包裹（不碰骨架）。
