我再把 B 的细节做实一层——尤其 18 档的具体归属、R10 与 B-1 是否重复、以及 gap 修复对 h75 的连带影响。
先勘一个我自己上轮的数字：grep 截断导致我把 carriers 数成 18 档。完整解析 `config/recipes.json` 后是 **19 个 carrier 条目（phone 13 + shot 6）**；shot 的 6 条对应 5 个不同区间（`[48,52]` 在 R-note-01 light/dark 各一次）。DIAGNOSIS 的「shot 5 档」按唯一值数、「3 档必改」按条目数，两种口径混用——这本身就说明影响面清单不能直接当施工依据。
## 第一部分：现在这个「方案 B」到底有什么问题

### P1 · 三件异质的事被捆成一个阶段

|            | 性质               | 改动层        | 验证方式                 | 涟漪面           |
| ---------- | ------------------ | ------------- | ------------------------ | ---------------- |
| ① 镜像债   | 架构债（双事实源） | gate + config | 负例「后果层仍接住」实证 | 19 条 carriers   |
| ② h75 溢出 | 几何 bug           | seed          | 真实管线 R1 复验         | 2 个骨架         |
| ③ gap 覆盖 | CSS 优先级 bug     | seed 一行     | 41 图重渲 + 全量回归     | **全部 41 骨架** |

§8.5.3 把 ③ 写成「搭车项：同一次 SHA 三处同步，省一轮」。但 ③ 改的是 `.region{gap:2.4cqw}` 的优先级，所有 `class="region heading"` 骨架的 head 都会少 2cqw、wall 多 21.6px——它改变的是**全部页面的垂直几何基准**，涟漪面比 ①+② 加起来还大，而且它是 A 与 h75 共同的 upstream 根因。把根因当搭车项，是 B 当前定义里最实质的排序错误。

### P2 · 影响面清单失真，且漏了两处会让施工直接崩的硬阻塞

- `tools/project.mjs:89` 强制 `carriers.width` 必须是 `[1,108]` 区间 → **删字段后 LOAD 层直接拒建**，不是 gate 报错是根本跑不起来。`test-controlled.mjs:410` 的 `layout-carrier-width-out-of-range` 夹具也依赖这条校验。
- `tools/validate.mjs:102` 裸读 `carrier.width[0]`，无缺省保护 → 删字段后 gate 抛 TypeError。
- 负例迁移未量化：184 条里 11 条命中 R14，`skeleton-carrier-width`、`skeleton-shot-counts` 等直接靠宽度档拦截，删校验后会由 blocked 变 passed，需逐条重登记或显式接受残余。
- 回归口径仍写「178 负例」（TODO L135、§8.5.2），现行 184。

§8.5.2 的影响面表只列了 4 行，`project.mjs` 与夹具重登记都不在里面。按它施工，第一刀就会卡在加载层。

### P3 · B-2 的删除范围自相矛盾

§8.5.1 写「config 删 phone 的 width 字段」＝ 13 条全删；§3.1/§3.2 写「镜像债只涉及带固定高度档的 phone（h68/h75），不涉及 shot」＝ 只删 3 条。中间 10 条普通 phone 档该算镜像还是区间约束，文档没有答案。这不是措辞问题，是施工范围未定义——判据不定死，两刀会做出两个不同的架构。

### P4 · B-1 不只是「概念上仍两处」，还和 R10 重复

`validate.mjs:213-220` 的 R10 已经遍历所有声明 `aspect-ratio` 的元素（含 `.phone`），用 `skew > 1.01` 检查实际宽高比是否等于 `910/1806`。B-1 的「从 seed 高度档派生期望宽度再校验」本质上是对同一个数学等式的第二次执行。所以 B-1 不是「治一半」，而是**新增一条与 R10 重复的 gate 规则**，比现状更违反单一所有权。这条上一轮我只说了概念，实证后结论更硬：B-1 应当直接排除，不必留作候选。

### P5 · h75 与 h68 结构不同，「一模一样的病」不成立

实测两个 h75 骨架（`card02-centered`、`note02-phone-dcards`）都是 `data-region="left"` 里裸放 `class="phone h75"`，**没有 `.phone-cell`、没有界面名标签**；h68 则是 phone-cell 内「手机 734.4 + gap 15.1 + 标签 31.8 = 781.3px」。所以 h75 的溢出取决于 left 列高，不是 wall 高，§3.1「更需要高 wall 区」表述不严谨。更关键的是：gap 修复会让所有 body 多 21.6px，h75 的压力反而**减轻**。因此「h75 弹性化」不该预设为 B 的必做项，应降级为「gap 修完后用真实素材压力测试，按数据决定」。

### P6 · 立项时机存在循环依赖

§8.5.3 定「A1 先行，按 h75 实测决定 B 是否提前」。但 A1 跑的是现行 R14，而现行口径带 §8.6 的 gap 病；用带病 gate 测出的骨架病清单，既混了 seed 病，又会在 B 改完 R14 后整体失效。同时 TODO L135 已预告 T14 喂长文案会触发 h75 R1——B 若拖到 T14 后，7 页验收数据本身失真。

## 第二部分：我提供的方案

### S0 · 先把「单一原则」写成可核对的判据

不写口号，写三条能逐条打勾的：
1. **事实只在一处定义**——高度档只在 seed；宽度由 `aspect-ratio:910/1806` 派生，不进 config。
2. **gate 只查后果**——R1 溢出 / R10 比例失真 / R14 保留的 share·headline·anchor；不复述 CSS 已锁定的值。
3. **砍规则前先证伪**——被砍规则对应的坏例，必须逐条给出「仍被后果层接住」或「显式接受残余」的夹具编号（T6-C2/C3/C5 同一纪律），拦不住的回炉后果化，不许硬删。

由此派生出分类判据：**是否存在一个需要与 seed 手工同步的独立高度事实源**，而不是 `component == phone`。这就是上图三分类的依据——只有 3 条真镜像删 width，其余 16 条（普通 phone 10 + shot 6）保留，它们是「防载体被压窄」的后果区间，不是第二份事实。

### S1 · 立项形态：一个定案 + 两刀施工，不是把 §8.5 直接开工

| 步骤                       | 产出物                                                       | 回归                |
| -------------------------- | ------------------------------------------------------------ | ------------------- |
| **B-定案**（纯文档，1 轮） | ① 19 条 carriers 逐条定性表 ② 删除范围判据 ③ 被砍规则的坏例清单与后果层实证方案 ④ gap / h75 的先后与合并裁决 ⑤ 两处硬阻塞的改法 | 无                  |
| **第 1 刀 B-seed**         | 修 §8.6 gap（根因收口）；seed + SHA 三处同步 + 41 图重渲；h75 **不动**，改用真实素材压力测试决定是否还需弹性化 | 全量负例 + 索引重建 |
| **第 2 刀 B-contract**     | 删 3 条真镜像 width；顺序不可倒：**先改 `validate.mjs` 让 width 缺省可跳过、`project.mjs:89` 允许缺省 → 再改 config → 最后重登记夹具** | 全量负例 + 索引重建 |

两刀分开 commit（项目纪律），但 seed 侧只走一次 SHA 三处同步，避免为 gap 和 h75 各跑一轮 41 图重渲。

### S2 · 排程：推荐 B 在 A1 之前，并补一个历史断面

|            | 甲：B → A1 → T14（推荐）   | 乙：A1 → B → T14（§8.5.3 原案）          |
| ---------- | -------------------------- | ---------------------------------------- |
| A1 口径    | 干净 gate                  | 现行带 gap 病，且 B 后必变，等于白测一轮 |
| 骨架病清单 | 不含 seed 病               | 混入 seed 病，难归因                     |
| T14 风险   | 已消解                     | 需保证 B 赶在 T14 前                     |
| 代价       | 失去「现行 gate 下的基准」 | 多一轮回归                               |

补一句边界：若 §5.4 判据 3「回归不破」需要旧口径做对照，就在 B 前先存一份 41 骨架的现行 gate 报告作为**只读历史断面**（同 11-11 两快照纪律，不删不改），而不是为了留基准把 B 推后。

### S3 · 验收判据（B 做完怎么算成功）

1. seed 的 h68/h75 高度档是唯一几何真源；config 不再存任何由它派生的宽度区间；R14 不再复述宽度。
2. 被砍的 3 条 width 校验各有对应夹具编号，明确写出「被 R1/R10 接住」或「显式接受残余」。特别要实证**等比缩放**这类坏例：等比缩放不改变宽高比，R10 静默，可能谁都拦不住——这正是 §8.5.1 风险预登记要求实测的点。
3. 全量负例（184 → 新基线）全绿、索引 drift 0、种子/资产/索引三把锁零涟漪。
4. 41 骨架 `_sc` 重渲；h68、h75 灌真实感长文案跑真实管线，R1 清零。
5. 账目四处刷新：19 条 carriers 定性表、种子 SHA 三处、`178→184` 口径、旧 `5318D18B…` 四处残留。

### S4 · 我明确不主张的

不把 gap 当搭车项（它是根因，独立成刀）；不采纳 B-1；不把 13 条 phone 一刀切全删；不预设 h75 必做弹性化；不把两刀合并成一笔 commit；不让 B 拖到 T14 之后。
